## Reading the numbers

- `exact_token` questions ask for a literal service/error-code pair. This is the case the assignment expects dense retrieval to fail; see the verdict below for what this corpus actually measured, which is reported as-is rather than as expected.
- `paraphrase` questions are deliberately hard: the seeded postmortems share one body template, so a paraphrase has no distinguishing content to lock onto. They are still the cleanest demonstration of dense-vs-sparse complementarity, because they contain no identifier tokens for BM25 to match.
- `filtered` questions are solvable by any strategy that honours the filter, so they mostly verify that metadata filtering is pushed into the store.

### Verdict

- Best strategy on MRR: **hybrid (RRF)** (0.9214).
- On `exact_token` questions: sparse 0.8500, dense 0.9000 (gap -0.0500). Dense leads here, which is NOT what the assignment predicts. The cause is corpus shape rather than a property of dense retrieval: the seeded documents are short and templated, so an identifier appears verbatim in a tight, repeated context that MiniLM encodes well. The gap in sparse's favour would widen on real postmortems, where the same code appears in varied prose. Reported as measured rather than re-labelled to match the expectation.
- On `paraphrase` questions the ordering flips: dense 1.0000 vs sparse 0.3000. The two retrievers fail in opposite directions, which is the actual justification for hybrid: neither one alone covers both query shapes.
- Hybrid MRR 0.9214 vs the better single retriever 0.8571 (+0.0643). Fusion is a net win.
- On `exact_token` specifically, fusion lifts dense-only by +0.1000 (0.9000 -> 1.0000), which is the combination the assignment is really asking for.
- Reranking changes MRR by -0.0571 (0.9214 -> 0.8643) at k=5.
  Recall@5 moves +0.0057 at the same time, so reranking trades ordering quality for coverage.
  It lifts single-document `structural` questions (where the right chunk exists but fusion under-ranks it) and drops `exact_token` questions: a runbook mentions the service+code pair more compactly than the postmortem does, so a query-level scorer prefers it. Net negative on this corpus, so it is disabled by default in `config.yaml`. It stays implemented and selectable per request so the trade-off can be re-measured on a different corpus rather than argued about.
