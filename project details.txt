Objective
An on-call engineer is paged at 2 AM. Something is wrong with a service, and somewhere in the organization's history is a postmortem describing the exact same failure from eighteen months ago - which nobody remembers. Build an assistant that answers questions like "checkout p99 is spiking and the DB connection pool looks saturated - has this happened before?" against a corpus of past incidents, runbooks, architecture docs, and alert definitions.
What makes this project technically interesting, and why it was chosen over a generic "chat with your docs" build:
Queries mix two retrieval modes. "checkout-service", "ERR_POOL_EXHAUSTED" and "p99" are exact tokens that keyword search finds and embeddings blur. "the thing where requests pile up and everything slows down" is pure semantics. One retrieval strategy cannot serve both - hybrid search is a requirement, not an optimization.
Documents have meaningful internal structure. A postmortem has a timeline, a root cause, and a remediation section. Naive fixed-size chunking cuts a root cause in half and retrieves a fragment that means nothing. Chunking must respect document structure.
Memory is forced, not decorative. An incident conversation runs for hours. By message 40, the context window is gone - but "we already ruled out the deploy at 01:15" must survive. If the assistant re-suggests a ruled-out hypothesis, it is worse than useless during an incident.
Retrieval failure is normal. Many questions genuinely have no matching past incident. An assistant that confidently invents a precedent is actively dangerous at 2 AM.
The goal of this assignment is to evaluate: hybrid RAG design, structure-aware ingestion, three-layer memory management, LangGraph self-correction loops, and honest handling of retrieval failure.

Ingestion requirements:
Structure-aware chunking. A postmortem's Root Cause section must be chunked as a coherent unit, never split mid-section. Document your chunking strategy per document type and justify the sizes you chose
Metadata on every chunk - at minimum: document type, service(s) mentioned, severity, date, section name, error codes present. This metadata is what makes filtered retrieval possible later
Entity extraction at ingest time - service names, error codes, and dependency relationships extracted into a structured store, not just embedded. Some questions ("which services depend on the payment gateway?") are graph lookups, not similarity searches, and answering them from embeddings is the wrong tool
Re-ingestion must be idempotent - running the pipeline twice must not duplicate chunks
Retrieval (the core)
Hybrid search: dense (embeddings) + sparse (BM25/full-text) run in parallel, with results fused. Implement the fusion yourself - reciprocal rank fusion or a weighted score - and justify the weighting with measured numbers, not intuition
Metadata filtering: "show me only SEV1 incidents involving checkout-service in the last year" must filter before or during retrieval, not by fetching everything and filtering in application code
Re-ranking: top-k from fusion goes through a re-ranking pass (cross-encoder, or an LLM-based re-ranker). Measure and report retrieval quality with and without re-ranking - if it doesn't help on your corpus, say so with evidence rather than keeping it because it's standard
Custom LangChain retriever: wrap all of the above as a proper retriever class so it composes with the rest of the LangChain ecosystem
The LangGraph Pipeline

Required behaviors:
Router node decides the path: entity/graph lookup, retrieval, or direct answer (a question like "what does p99 mean?" needs no retrieval and should not pay for it)
Grading node judges whether retrieved chunks actually answer the question - not whether they are topically similar
Rewrite cycle: failed grading rewrites the query and retries. Bounded - an unbounded rewrite loop is a cost incident. Define the cap and what happens when it is hit
Ground check: before the answer reaches the user, verify every factual claim traces to a retrieved chunk. A claim that doesn't must be removed or flagged, not shipped
The honest-failure path: when retrieval genuinely finds nothing relevant after the bounded retries, the system must say so plainly and say what it did search. This path must be demonstrated, not just coded
Stream graph events to the client - the user sees which node is executing, not a spinner
Memory Management
Three layers, all three implemented:
Working memory - recent conversation turns, verbatim.
Summary memory - older turns compressed. The compression must be incident-aware: a generic summarizer will happily drop "we ruled out the 01:15 deploy" as conversational filler. Design your summarization prompt and triggering policy so that ruled-out hypotheses, confirmed facts, and actions already taken survive compression. Document what you deliberately preserve and what you let go.
Entity memory - structured facts accumulated during the conversation:
{
  incident_id,
  services_implicated: [],
  hypotheses: [ { text, status: open|ruled_out|confirmed, evidence } ],
  actions_taken: [ { action, timestamp, outcome } ],
  timeline_anchors: []
}

This is queried and injected on every turn, separately from the conversation history.
Additional requirements:
Conflict resolution: the engineer says "actually the deploy was the cause" after it was marked ruled out. The entity memory must update rather than hold both contradictory states. Implement and demonstrate this
Token budgeting: allocate the context window explicitly across system prompt, entity memory, summary, recent turns, and retrieved chunks - with reserved output headroom. Expose the actual per-request allocation through an API so it is observable
Eviction order: when the budget is exceeded, something must go. Define the order, justify it, and demonstrate a conversation long enough to trigger it while remaining coherent
Retrieval Evaluation (mandatory)
Build a small evaluation harness - "it seems to work" is not an acceptable answer for a retrieval system:
A hand-built eval set of at least 25 questions with known correct source documents
Measure retrieval quality (precision@k / recall@k or MRR - pick and justify)
Measure answer groundedness - what fraction of claims are supported by retrieved context
Report a comparison table: dense-only vs sparse-only vs hybrid vs hybrid+rerank, with real numbers from your corpus
Re-runnable as a script, with results in the README

Trace Viewer (required)
A minimal UI showing, per message: which graph path executed, the retrieved chunks with their fusion and rerank scores, whether grading passed or triggered a rewrite, the ground-check result, and the token budget breakdown. You cannot debug a RAG system you cannot see, and this viewer is what you will use for the rest of the project.
Technical Requirements
LangChain callbacks wired for full observability - every LLM call, retrieval, and chain step logged with latency and token counts
LLM response caching for identical prompts during development (this saves real money while iterating on the graph)
Retrieval timeout - a hanging vector store must not hang the request
Structured JSON logging, request ID threaded through the entire graph execution
Config-driven: chunk sizes, fusion weights, top-k, rewrite cap, and token budget must all be configurable without code changes

Important Instructions
Dense-only retrieval fails this assignment regardless of how well the rest works - the error-code case is the entire reason hybrid is required
Fusion weights chosen by intuition with no eval numbers behind them lose the retrieval marks
A summarizer that drops ruled-out hypotheses fails the memory section - demonstrate that it doesn't
The no-answer path must be demonstrated live. A system that always finds something is hallucinating, not retrieving
